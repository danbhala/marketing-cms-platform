The app does not import blocks. It renders pages through the component registry, which maps every block type to a component:

```ts title="packages/component-registry/src/index.ts"
export function createRegistry(overrides: Partial<BlockComponentMap> = {}): Registry {
  const components: BlockComponentMap = { ...blockComponents, ...overrides }
  return {
    components,
    get: (type) => components[type],
    has: (type): type is BlockType => type in components,
    types: Object.keys(components) as BlockType[],
  }
}

export const registry: Registry = createRegistry()
```

The route spreads that map and rebinds the two listing blocks, which need the request's locale and URL, before handing it to the template:

```tsx title="apps/web/app/[locale]/[[...slug]]/page.tsx"
const components = {
  ...registry.components,
  collection: createCollectionBlock({ locale, basePath, searchParams, draft: draftCtx }),
  latestNews: createLatestNewsBlock({ locale, draft: draftCtx }),
}

<PageTemplate page={doc} settings={settings} components={components} breadcrumbs={breadcrumbs} siteUrl={siteConfig.siteUrl} />
```

That is already the pattern: the app customises the map and `packages/ui` stays generic. Because the seam is a plain object keyed by block type, three further customisations need no change to `packages/ui`.

## Override a block

Replace the component for one type. The override must accept the same props, so the content model and the CMS schema are untouched and editors notice nothing:

```tsx title="apps/web/components/brand-hero.tsx"
import type { HeroProps } from "@platform/ui/blocks"
import { BlockSection, Container, Heading, ActionGroup } from "@platform/ui"
import { fieldAttrs } from "@platform/cms-core/edit"

/** A full-bleed hero for this brand. Same content model as the stock Hero. */
export function BrandHero({ block, className, ...props }: HeroProps) {
  return (
    <BlockSection block={block} spacing="lg" className={className} {...props}>
      <Container>
        <Heading as="h1" size="display" {...fieldAttrs(block, "title")}>
          {block.title}
        </Heading>
        <ActionGroup actions={block.actions} {...fieldAttrs(block, "actions")} />
      </Container>
    </BlockSection>
  )
}
```

```ts title="apps/web/lib/registry.tsx"
import { createRegistry } from "@platform/component-registry"
import { BrandHero } from "@/components/brand-hero"

export const registry = createRegistry({ hero: BrandHero })
```

Then import `registry` from `@/lib/registry` in the page route instead of from the package; the per-request listing bindings spread on top as before. `HeroProps` is `BlockComponentProps<HeroBlock>`, so the override is type-checked against the same content as the original.

Prefer editing the block in `packages/ui` when the change should apply everywhere (Storybook, the docs, the tests, every site built from this code). Use an override when one site diverges and the rest should not.

## Wrap a block

A wrapper keeps the stock component and adds something around it or to it. This is how a [prop the CMS does not know about](/docs/customising/variants-and-props#adding-a-prop) gets set:

```tsx title="apps/web/lib/registry.tsx"
import { createRegistry } from "@platform/component-registry"
import { Stats, type StatsProps, Pricing, type PricingProps } from "@platform/ui/blocks"

export const registry = createRegistry({
  // A prop the component exposes.
  stats: (props: StatsProps) => <Stats {...props} align="start" />,
  // Anything a <section> accepts falls through BlockSection: analytics hooks, ids, classes.
  pricing: (props: PricingProps) => <Pricing {...props} data-track="pricing-table" className="scroll-mt-24" />,
})
```

Wrappers can also render around the block (a decorative background, an `IntersectionObserver` client component for animation, a feature flag that hides the section) as long as they pass `block` and `index` through.

## Slot into the page

`PageTemplate` and `BlockList` are the composition points above blocks:

```ts title="packages/ui/src/templates/page-template.tsx"
export interface PageTemplateProps extends React.ComponentProps<"div"> {
  page: Pick<Page, "blocks" | "theme" | "hideBreadcrumbs" | "$edit">
  settings: SiteSettings
  components?: Partial<BlockComponentMap>
  breadcrumbs?: Crumb[]
  siteUrl?: string
  /** Slot rendered before the blocks, e.g. a preview banner in draft mode. */
  before?: React.ReactNode
  /** Content rendered inside `<main>` above the blocks (an article's header and body). */
  children?: React.ReactNode
}
```

- `before` renders between the header and the first block: a preview banner, a cookie notice, a hard-coded section the CMS should not control. `children` renders inside `<main>` above the blocks; `ArticleTemplate` uses it for the article header and body, and a bespoke document type can do the same.
- `components` is the registry map, so a route can pass a different one (a campaign route with its own hero).
- For a page layout the template does not cover, compose `AnnouncementBar`, `SiteHeader`, `BlockList` and `SiteFooter` yourself; they are exported from `@platform/ui/templates` and `BlockList` takes the same `components` map.
- Hand-built pages (a 404, an app page outside the CMS) can use any block directly with a literal `block` object, or the block's parts: `SectionHeader`, `ActionGroup`, `PriceCard`, `Quote` and the other molecules are exported for that reason.

## Inject framework components

`packages/ui` renders plain `<a>` and `<img>` until the host injects its own. The app does it once in the root layout:

```tsx title="apps/web/components/ui-provider.tsx"
export function UiProvider({ children }: { children: React.ReactNode }) {
  return (
    <BaseUiProvider Link={Link} Image={Image}>
      {children}
    </BaseUiProvider>
  )
}
```

`Link` wraps `next/link` and `Image` wraps `next/image` with the canonical `Media` shape. Providers nest and merge, so one route can swap only `Image` (a different loader, a CDN with its own URL scheme) and keep the app-level `Link`. This is also the place to add a tracking wrapper around every link on the site without touching a block.
