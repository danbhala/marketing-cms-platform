title: Variants and props
description: "Add a layout or style option editors can pick, or a prop the CMS never sees."
---

Two kinds of knobs look similar but live in different places. A **variant** is a choice editors make per block, so it is a `select` field in the content model and a CVA variant in the component. A **prop** is something the site developer decides (alignment, analytics attributes, a slot), so it stays out of the CMS and is set where the block is rendered.

## Adding a variant

Layout variants are CVA variants, not separate components. The Hero's four layouts share one markup:

```tsx title="packages/ui/src/blocks/hero.tsx"
const heroLayout = cva("grid items-center gap-10 section-lg:gap-16", {
  variants: {
    layout: {
      centered: "grid-cols-1 justify-items-center text-center",
      split: "grid-cols-1 section-lg:grid-cols-2",
      splitReverse: "grid-cols-1 section-lg:grid-cols-2 section-lg:[&>*:first-child]:order-2",
      background: "grid-cols-1 justify-items-center text-center",
    },
  },
  defaultVariants: { layout: "centered" },
})
```

To add a left-aligned layout with the media underneath:

<Steps>
<Step>
### Add the option to the field

```ts title="packages/content-model/src/definitions/blocks.ts"
layout: field.select(["centered", "split", "splitReverse", "background", "left"] as const, { // [!code highlight]
  defaultValue: "centered",
}),
```

`HeroBlock["layout"]` now includes `"left"`, the validator accepts it, and after `pnpm schema:generate` the dropdown in every CMS offers it.

</Step>
<Step>
### Add the CVA variant

```tsx title="packages/ui/src/blocks/hero.tsx"
layout: {
  centered: "grid-cols-1 justify-items-center text-center",
  split: "grid-cols-1 section-lg:grid-cols-2",
  splitReverse: "grid-cols-1 section-lg:grid-cols-2 section-lg:[&>*:first-child]:order-2",
  background: "grid-cols-1 justify-items-center text-center",
  left: "grid-cols-1 justify-items-start text-left", // [!code ++]
},
```

CVA's `VariantProps` infers the union from this object, so if the select options and the variant keys drift apart TypeScript reports it at `heroLayout({ layout })`. Any branches in the component (`centered`, `background`) decide what the new option does with media, actions and alignment.

</Step>
<Step>
### Add a story

```tsx title="packages/ui/src/blocks/hero.stories.tsx"
export const Left: Story = {
  args: { block: { ...fixtures.heroBlock, layout: "left" } },
}
```

The story is the test (`pnpm test` renders it with axe) and the screenshot for the block page.

</Step>
</Steps>

The same applies to style options: `featureGrid.itemStyle` (`plain` / `card`), `logoCloud.grayscale` (a `boolean`), `stats.columns` and `stats.countUp` are all CMS fields read by the component, and the shared `animation`, `headingAnimation` and `animationStagger` fields in `presentation` work the same way for every block (see [Animation](/docs/animation)). The `Grid` atom already has column variants `1` to `6`, so letting editors pick five columns on the Stats block is the select option plus one branch of the `divide` expression.

## Adding a prop

Blocks accept every `<section>` attribute as well as `block` and `index`:

```ts title="packages/ui/src/blocks/block-section.tsx"
export interface BlockComponentProps<B> extends Omit<React.ComponentProps<"section">, "children"> {
  block: B
  index?: number
}
```

`className`, `id`, `aria-*` and `data-*` fall through to `BlockSection` and onto the `<section>`. For a prop of your own, extend the props type and read it in the component:

```tsx title="packages/ui/src/blocks/stats.tsx"
export interface StatsProps extends BlockComponentProps<StatsBlock> {
  /** Alignment of each number; the CMS does not control this. */
  align?: "start" | "center"
}

function Stats({ block, index, align = "center", className, ...props }: StatsProps) {
  // …
  <StatItem key={stat.id} item={stat} align={align} className="px-4" />
```

The page renderer only passes `block` and `index`, so a prop needs somewhere to be set. That is the registry: wrap the block with the prop applied and register the wrapper, as [Registry and wrapping](/docs/customising/registry-and-wrapping) shows. Molecules take props the same way; `StatItem` already has `align` and `countUp`, and `ActionGroup` has `size`, `align` and `stackOnMobile`.

## Which one?

|                     | Variant (field)                   | Prop                                                               |
| ------------------- | --------------------------------- | ------------------------------------------------------------------ |
| Who decides         | Editors, per block                | Developers, per site or per route                                  |
| Lives in            | `defineBlock` fields + CVA        | The component's props type                                         |
| Shows up in the CMS | Yes, after `pnpm schema:generate` | No                                                                 |
| Set from            | Content                           | The registry, a page template, or a bespoke block that composes it |

When in doubt, start with a prop. Promoting it to a field later is additive; taking a field away from editors is a breaking content change.
